# AI Software Factory OSS 1.5.0

Release tag: `v1.5.0`.

Version 1.5.0 is a focused productization release over `v1.4.0`. It keeps the
repository-first authority, bounded recovery and audit model unchanged while making
the framework easier for a new Human or AI Agent to enter, acquire and use safely.

## What changed since 1.4.0

### Clearer first-contact routing

The English and Simplified Chinese README now expose a concise **Start here** path:

- new Human users go to Quickstart and the recommended ChatGPT/Codex role setup;
- AI Agents go to `AGENTS.md` and then `AI_ENTRYPOINT.md`;
- operators who want a fresh-context consistency audit go directly to Fresh Factory
  Audit guidance or the native GitHub New Issue template.

The goal is to reach the smallest useful path before asking a new user to learn the
whole mechanism set.

### Exact-release acquisition and Windows-friendly first run

Quickstart now explains how to obtain a reproducible release locally through either:

- GitHub Release **Source code (zip)** for users who do not use Git; or
- Git clone plus an exact release-tag checkout.

It also includes Windows PowerShell / `py -3` equivalents for release verification
and the first local commands. No third-party Python package or model API key is
required for the synthetic exercises.

### Minimal safe AI boot for bounded work

`AI_ENTRYPOINT.md` now separates a full initial boot from a **minimal safe boot**.
The minimal path is available only when the instance, project, role and work surface
are already selected and there is no known authority or environment conflict.

The bounded sequence is current authority/state -> active work/checkpoint/evidence
-> relevant Git/ref/environment facts -> blockers/Human gates/next safe action.
Read scope expands only for a concrete dependency, conflict, missing fact, authority
change or assigned audit. Missing prerequisites still fail closed or require the
full boot.

### Cockpit example alignment

The checked-in Project cockpit is now prominently marked as a static/legacy teaching
snapshot. It remains useful for browsing, but users are directed to the current
schema-2 generator when they want the latest generated work-item/checkpoint package
shape.

### Native Fresh Factory Audit entry

Fresh Factory Audit now appears in GitHub's native **New issue** chooser. The native
template preserves the same safety contract as the reusable template: repository
evidence remains authoritative, generated views are derived, the audit is read-only
and fail-closed, and findings do not self-authorize remediation, extra Issues, Issue
state changes, merge, release, publication, deployment, credential use, production
or destructive action.

### Post-publication wording normalization

Current repository documentation no longer describes the already-published
`v1.4.0` release as a future publication action. The historical `v1.4.0` tag itself
was not moved or rewritten.

## Public/private and authority boundaries

No new authority model is introduced by 1.5.0. A model name, chat identity, GitHub
account, generated cockpit, Project view, skill output or connected tool does not
become organizational authority. Unknown facts remain UNKNOWN and affected actions
stop or expand to the required authoritative evidence.

All distributed examples remain synthetic. Private Factory history, real
appointments, company/customer facts, credentials and production evidence must not
be copied or renamed into public examples.

## Security and limits

The repository uses GitHub Private Vulnerability Reporting and does not publish a
personal vulnerability-reporting email. See [SECURITY.md](../../SECURITY.md).

The framework does not provide autonomous scheduling, authenticated mail transport,
production deployment, secret management or automatic private/public synchronization.
Validators and generated views check declared repository relationships; they do not
prove real organizational authority, evidence authenticity, OS isolation or
external-system permission.

## Release integrity

`v1.4.0` is historical and immutable. If `v1.5.0` is published, its tag must point
to the exact final release commit produced by the release-candidate flow and must
not later be moved. Release preparation and publication evidence is recorded on the
v1.5.0 release coordination Issue.
