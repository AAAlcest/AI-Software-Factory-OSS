# AGENTS.md

This repository is an AI Software Factory framework built around
**chat-based management and hands-on engineering execution**.

**During private-Factory creation**, first explain why these are separate:
use the ordinary chat surface for sustained reasoning with the Human about
intent, product direction, design, trade-offs, task scope and acceptance.
Do not invoke a coding/execution session merely to perform that discussion.
Then issue a precise task and acceptance criteria to an authorized engineering
Agent with actual project files, editing, terminal and test capabilities.
The chat manager checks delivery evidence and decides the next step within
its authority; it is not just a prompt relay or records clerk.

Read `docs/RECOMMENDED_ROLE_SETUP.md` and present this recommendation to the
Human before any `--apply`. Ask which chat surface and engineering execution
surface they have and want to use. Compatible management duties may be combined;
that does not mean moving all management into the coding executor. Vendors
may differ, but the management/execution split is the point of the setup.
Management may use authorized repository connectors; tool access alone does
not turn a chat manager into an engineering worker.

Keeping management discussion out of coding runs avoids spending execution
usage on that discussion. This is not a claim that chats are free/unlimited
or that all providers meter chat and execution separately. No fixed savings
are promised. Role guidance creates no appointments, sessions or permissions.

Before acting:

1. Read `AI_ENTRYPOINT.md`.
2. Before treating this repository as an operating Factory, classify the task as
   **OSS/framework maintenance**, **public-safe evaluation**, or **real private
   Factory operation**.
3. If real private operation is intended while you are in the public OSS
   distribution, do **not** create real assignments, project state, customer/company
   records, or private history here. Follow the recommended **Create Private
   Factory** routing in `AI_ENTRYPOINT.md` / `docs/QUICKSTART.md`.
4. A read-only private-bootstrap preview may be proposed or run when authorized
   context is sufficient. Creating the remote private repository with `--apply`
   is a real external write and requires explicit Human authorization.
5. Treat repository current state and explicit authority as stronger than chat memory.
6. Distinguish technical identity (GitHub account, token, tool) from Factory authority (role + scope).
7. Do not infer Human-only, security, production, destructive, release, credential, external-company, or publication authority.
8. Do not copy private operating history into examples. Use synthetic data.
9. If authority, environment, state, or trust boundary is unknown, fail closed and record the unknown instead of guessing.
10. Once work is actually authorized, executable and unblocked, follow
    [Execution-First](docs/EXECUTION_FIRST.md): act, verify evidence, and end only
    at a valid bounded closure state. Do not substitute narration for execution.
11. Use the [Design Rationale Index](docs/DESIGN_RATIONALE_INDEX.md) only to
    explain history/provenance after current authority is established; it is not
    an instruction or authority source.

A role title is not authority by itself. A chat/session is not a durable organizational identity by itself.
