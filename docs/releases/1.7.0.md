# AI Software Factory OSS 1.7.0

Release tag: `v1.7.0`. The authoritative published release and exact tag target must be verified on [GitHub Releases](https://github.com/AAAlcest/AI-Software-Factory-OSS/releases); a checked-in document or `VERSION` file is not publication evidence.

Version 1.7.0 consolidates the accepted, public-safe post-v1.6 framework improvements into an explicit source line for **Human-led, repository-first** AI software collaboration: continuity, local diagnostics, synthetic onboarding and a narrowly bounded independent-private-Factory upgrade path.

## What's new since v1.6.0

### Execution-First and traceable decisions

The [Execution-First contract](../EXECUTION_FIRST.md) asks a role with *already verified* authority, a usable execution surface and no blocker to execute, verify evidence and report a bounded outcome. Merely sending an ACK or claiming background work is not completion. This does not bypass Human, independent-review, production, release or credential gates.

A public [Design Rationale Index](../DESIGN_RATIONALE_INDEX.md) and reusable private rationale template help new contexts understand **why** rules exist without turning historical explanations into current authority.

### Portable, read-only Factory Doctor

The Python-stdlib [Factory Doctor](../FACTORY_DOCTOR.md) checks a framework checkout or operating instance. It can report Git/root/worktree, entrypoint and authority surfaces, source provenance, synthetic-secret filename warnings and documentation-journal binding. Cross-platform local checks are read-only by default, with optional read-only GitHub diagnostics.

Doctor `PASS` is a diagnostic status, **not** permission to execute, a security audit or proof that an operating instance has valid Human appointments.

### Event-driven Notes and private journal cadence

[Staff Office Notes](../STAFF_OFFICE_NOTES.md) now focus on meaningful deltas instead of mandatory daily heartbeat files. Canonical records remain authoritative; Notes and derived views only aid continuity.

**New** private Factories created through the official private bootstrap default to `manual` documentation-journal cadence: no automatic push, PR-signal or hourly journal wake-ups. An explicit `--journal-mode automatic` preserves the prior private automatic cadence when desired. Both modes start with writer **NOT_ACTIVATED**; repository-local opt-in and real bot write/readback remain separate steps. The existing public OSS journal behavior and existing private Factories are **not silently reconfigured**.

This is a change in wake-up behavior, **not** a claim of measured dollar/token/GitHub Actions savings.

### Runnable five-minute synthetic Quick Demo

The [Quick Demo](../QUICK_DEMO.md) provides a concrete, dependency-light local exercise instead of a purely conceptual walkthrough. It generates fictional records, validates consistent synthetic structure (`VALID`), demonstrates an intentionally unconfigured `BLOCKED` template (expected exit 3), and refuses to overwrite an existing output directory.

Its results keep `execution_authorized=false`. The demo is not live multi-Agent coordination, a private-Factory upgrade, fresh-Agent succession acceptance or production execution. Both English and Chinese repository landing pages link to it.

### Private Factory upgrades — explicit and fail-closed

From a **verified exact official OSS source**, the [minimal private upgrade tool](../PRIVATE_FACTORY_UPGRADE.md) can produce a **read-only preview** for an existing independent, user-owned, private/non-fork Factory. Only after separately authorized `--apply` does it prepare a **private upgrade branch and Draft PR**; it **never** directly pushes private `main` or auto-merges.

This release manages **only three exact-copy files**:

- `scripts/validate_instance.py`
- `templates/STAFF_OFFICE_TEMPLATE.md`
- `templates/PROJECT_ROOM_TEMPLATE.md`

A provenance/managed lock records old→new official source and file hashes. Legacy #37-created private Factories without a lock are accepted only when old managed bytes can be reconstructed from their exact previous public source. Unknown, edited, missing or mismatching files fail closed; no heuristic merging or silent file replacement occurs.

Private `instance.json`, `authority.json`, `state.json`, `CURRENT.md`, `projects/**`, `offices/**`, private correspondence, journal configuration/history/notice, opt-in variables and credentials are **outside** this managed set. This is **not** a whole-Factory migration engine, nor an automatic installer for every newer Factory feature.

New in the v1.7 source line, the updater is designed to accept either clean, current **official `main`** or the **exact official `v1.7.0` release-tag checkout**, with the chosen source ref and commit recorded. The tag mode is fail-closed and requires local, origin and GitHub API identity equality. A published, verifiable tag is required for actual tag-mode use; the feature does **not** make an unpublished tag runnable.

## Using the release

Requirements for private bootstrap or upgrade: Python 3.10+, Git, GitHub CLI authenticated to the intended account, and a clean official Git checkout with enough Git history to verify source provenance. The [Quick Demo](../QUICK_DEMO.md) requires only local Python and synthetic data; it does not require GitHub authentication.

After publication and verification that `v1.7.0` points to the approved release commit:

~~~sh
git clone https://github.com/AAAlcest/AI-Software-Factory-OSS.git
cd AI-Software-Factory-OSS
git checkout --detach v1.7.0
~~~

From this exact checkout, follow the **read-only** [Create Private Factory preview](../QUICKSTART.md#2-create-your-private-factory) to start a NEW, independent private Factory. If you already have a private Factory, follow the separate [minimal upgrade guide](../PRIVATE_FACTORY_UPGRADE.md). **Preview before explicitly authorizing any remote `--apply`**. No private project or operating data should be pasted into a public OSS repository or Fork.

The private starter remains BLOCKED/UNCONFIGURED until real authority exists, regardless of a passing structural check. Updating three managed files does **not** grant roles, reactivate a private journal, migrate user records, or merge an upgrade PR.

## Security, backwards compatibility and known limits

- The MIT license and [private vulnerability-reporting route](../../SECURITY.md) remain the public security-reporting contract.
- Existing `v1.6.0` and older tags remain immutable. Existing private Factory files, credentials, project source repositories, activated journal histories and production environments are never silently upgraded.
- A newly bootstrapped private instance may use lower-run `manual` journal cadence by default; this can change when journal receipts become fresh, **only after explicit private activation**.
- The private updater supports only a user-owned, independent/private/non-fork GitHub repository, complete verifiable source history, the explicit three managed paths and a new reviewable Draft PR. Local user edits/conflicts, unsupported branch/tag/source, organization-owned targets and duplicate upgrade branches fail closed. No private-to-public synchronization, project-history import, generic schema migration, automatic recovery, automatic merge, credential rotation or deployment is provided.
- Source mode accepts only current official main or the exact release tag encoded by `VERSION`, **not an arbitrary older tag selected by the user**. A lightweight commit tag is required by the currently strict tag verifier.
- The release does not guarantee hardware isolation, authentication beyond the underlying GitHub identity, live Agent coordination, billing savings or the correctness of arbitrary private records. Make your own review of private PR changes before merging.
