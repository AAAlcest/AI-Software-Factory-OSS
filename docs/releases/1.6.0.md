# AI Software Factory OSS 1.6.0

Release tag: `v1.6.0`.

Version 1.6.0 turns the post-v1.5 onboarding and repository-governance work into a
reproducible private-Factory creation flow. The public OSS repository remains the
framework/distribution source; a user's real operating Factory can now be created
as a new independent private repository without requiring a GitHub Fork.

## What changed since 1.5.0

### GitHub-native documentation notice and journal

The public repository now has a durable documentation notice and an active
GitHub-native documentation journal. The recorder is repository-bound, metadata
only, fail-closed on identity/visibility mismatches, and uses verified Issue
receipts rather than an external always-on service.

The notice remains OPEN and UNLOCKED under the recorded Human-approved policy.
Public comments are not treated as trusted commands or organizational authority.

### Public-fork journal bootstrap

A public direct GitHub.com fork can initialize its own documentation notice and
writer configuration. The bootstrap is read-only by default, verifies the exact
fork/repository identity, and can enable Issues only on that verified fork when
the authenticated owner has sufficient access.

Forks remain a public OSS/contribution or public-safe evaluation surface. They are
not the recommended home for a user's private operating Factory.

### Create Private Factory

Normal private use no longer requires Fork.

From an exact official OSS source checkout, the new private-bootstrap command can:

- preview the intended destination and mutations with zero writes;
- create a NEW private, independent, non-fork GitHub repository only after explicit
  `--apply`;
- start a fresh Git history instead of copying the public OSS history;
- install a lean BLOCKED / UNCONFIGURED operating starter;
- preserve the MIT license and exact OSS source provenance;
- create one private OPEN / UNLOCKED documentation notice;
- adapt the existing documentation journal to that private repository;
- leave the writer disabled until a separate repository-local opt-in.

The generated starter does not invent a Human appointment, project, predecessor,
company authority, production access or private project history. Project source may
remain in separate private repositories referenced from the Factory.

### Reproducible release-tag bootstrap

The private bootstrap now accepts either:

- the clean exact official current `main`; or
- the clean exact official `v1.6.0` release-tag checkout.

No arbitrary branch, tag, fork or locally modified source is accepted. The created
private Factory records both the exact source SHA and whether its source ref was
`refs/heads/main` or `refs/tags/v1.6.0`.

This allows normal users to build from a stable published release rather than
following a moving `main`.

### Private journal safety and live acceptance

Private missing-Git-object retrieval uses the same repository's Actions token
through Git askpass; the token is not placed in the Git URL, argv, persistent Git
configuration, committed files or diagnostics.

The real private-bootstrap path was exercised end to end on a disposable private
repository under Human/PM control:

public OSS → read-only preview → independent private/non-fork repository →
BLOCKED starter/source provenance → private notice → writer-off dry run →
explicit repository-local opt-in → real bot write/readback → successful replay
with no duplicate receipt.

Only the public-safe PASS summary is retained in the public coordination Issue;
private repository names, paths, SHAs, run IDs and detailed private evidence remain
private.

### Fresh-Agent first-contact routing

README, `AGENTS.md` and `AI_ENTRYPOINT.md` now explicitly tell a fresh Agent to
classify its context before acting:

- OSS/framework maintenance;
- public-safe evaluation;
- real private Factory operation.

If a private Factory already exists, the Agent should enter that instance rather
than create another one. If real private operation is intended and no private
Factory exists, the recommended path is the read-only private-bootstrap preview,
an explanation of the privacy/mutation boundary, explicit Human authorization for
`--apply`, then continued operating work inside the verified private repository.

A fresh Agent may route to and perform the read-only preview. Creating remote
GitHub state remains Human-gated.

## Public/private and authority boundaries

The public OSS repository is a distribution and contribution surface. Real private
Factory state, appointments, company/customer information, credentials and private
history must not be placed in public OSS or public forks.

Repository access, a GitHub account, a model/chat identity, a green validator, a
documentation notice or a journal entry does not create organizational authority.
The private starter remains BLOCKED until real Human decisions and project/role
scope are recorded in that private operating repository.

## Security and limits

The private-bootstrap command creates remote GitHub state only with explicit
`--apply`; the normal preview is read-only. A partial failed apply is retained
privately for inspection rather than silently deleted or resumed.

This release does not include the private-Factory framework-upgrade lifecycle being
designed in Issue #39. It does not provide automatic migration of an existing
private Factory, autonomous production deployment, credential rotation, secret
management or private/public state synchronization.

See [SECURITY.md](../../SECURITY.md), the
[public privacy standard](../PUBLIC_PRIVACY_STANDARD.md), and the
